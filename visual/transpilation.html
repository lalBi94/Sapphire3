Ce que Sapphire 3 traduit, cible par cible

Le même modèle logique alimente trois backends : JavaScript, Python et un C expérimental. Cette page dit exactement ce que chacun accepte, comment les fonctions et opérations SP3 sont reliées à leurs équivalents, et ce qui est refusé avant toute émission de code.

1 · Chaîne commune

La transpilation n’est jamais automatique. Le document source, l’AST, les portées, les types et les diagnostics restent indépendants du langage cible. Une action explicite lance la chaîne suivante.

  1. analyzeProgram() construit l’AST, les symboles, les types et les diagnostics.
  2. Les gardes globales refusent les projets contenant une carte widget ou d’entrée, quelle que soit la cible.
  3. createGenerationContext() réserve les noms, résout les imports et les références, prépare les classes et le point d’entrée.
  4. Le backend choisi émet un fichier ou un extrait, avec ses propres helpers.
  5. Les diagnostics du backend sont fusionnés avec ceux de l’analyse ; une erreur bloquante rend le résultat ok: false.

Un programme complet exige exactement un point d’entrée sans paramètre. Un aperçu de sélection (transpileSelection) n’exige pas de point d’entrée et ne produit jamais un fichier autonome. Les contrats attachés aux variables, constantes et paramètres sont vérifiés par le simulateur et le Run live ; ils ne sont pas émis dans le code généré.

Refus explicites avec TRANSPILE_C_UNSUPPORTED : tableaux, classes, lambdas capturantes et fermetures, ForEach, MathCall, conversions explicites, char, variables sans initialiseur et adresse d’une constante. Les pointeurs de fonction nommés et les lambdas sans capture sont acceptés ; Print d’un pointeur de fonction reste refusé. Le backend vérifie ces limites avant d’émettre le fichier.

Limites connues du C

  • Les globales non encore initialisées valent zéro avant leur affectation.
  • Un pointeur vers une variable locale ne doit pas survivre à sa fonction.
  • Les flottants de magnitude extrême peuvent différer du format JavaScript.
  • C++ et Java restent indisponibles.

6 · Fonctions et opérations

Un module n’est pas émis comme un objet d’exécution : ses fonctions deviennent des fonctions du langage cible, préfixées par le nom du module. Un import ne produit ni import JavaScript, ni import Python, ni inclusion C : la référence importée est résolue vers le nom généré de la fonction exportée. Le fichier reste autonome.

Une fonction ordinaire est émise une seule fois, avec ses paramètres concrets. Les génériques ne créent pas de copie : JavaScript/Python émettent la même fonction ordinaire et la simulation applique les types inférés. C refuse les types génériques. Les références de fonction sont des valeurs de première classe en JavaScript et Python ; C accepte les fonctions nommées via des pointeurs typés et lève les lambdas sans capture en fonctions statiques. Une lambda qui capture une variable locale ou un paramètre reste refusée, faute d’environnement de fermeture.

Le registre src/utils/logic/mathNatives.js est le catalogue unique des opérations natives SP3 : identifiant stable, catégorie, signature et groupe d’interface. Les backends ne recréent pas ce catalogue ; ils fournissent chacun une table de correspondance par identifiant : nativeJavaScript, nativePython, et le backend C refuse actuellement toutes les MathCall. Une opération présente dans le registre mais absente de la table du backend produit un diagnostic stable (TRANSPILE_EXPRESSION_UNSUPPORTED en JavaScript/Python, TRANSPILE_C_UNSUPPORTED en C).

Ajouter une opération

  1. L’ajouter au registre mathNatives.js avec sa signature et son groupe.
  2. Ajouter son émission dans nativeJavaScript et/ou nativePython.
  3. Si la cible C doit la porter, ajouter un helper et une émission C ; sinon la laisser refusée.
  4. Ajouter un test qui compare la simulation et le code généré.

7 · Refus et limites

Les refus sont des diagnostics stables, pas des traductions approximatives. Le projet reste inspectable et modifiable ; seule la génération est bloquée.

La suite de tests compile et exécute les fichiers C générés avec cc -std=c11. Les exemples Fibonacci, Recursion, Imports, Pointers, Higher-order et Calculus produisent la même sortie que le simulateur en C. Les tests couvrent aussi les lambdas sans capture et le refus des lambdas capturantes. JavaScript et Python couvrent en plus les tableaux, les lambdas, ForEach, les classes et les opérations natives prises en charge.
