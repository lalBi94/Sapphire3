Des blocs qui sont de vrai code, pas des dessins qui y ressemblent

Sapphire 3 est un environnement de programmation visuelle. Chaque carte posée sur le canvas est une construction du langage : une fonction, une variable typée, une boucle, un appel. Elles forment un arbre syntaxique indépendant du langage cible, qu'un moteur analyse, type et vérifie avant toute génération. Le texte n'a jamais été supprimé : il a seulement cessé d'être le point de départ.

État du projet

Sans emphase

Ce qui fonctionne aujourd'hui

Canvas navigable, zoom sémantique et cartes Module, Class, notes et images. Les classes proposent des membres public/private, un constructeur, des instances avec new, this et des types de classe. Pas d'héritage ni de polymorphisme ; les classes ne sont pas encore transpilées. Le langage couvre les fonctions et types déclarés à la racine d'un module, conditions, boucles, ForEach, affectations, appels, tableaux, typage statique strict, références de fonction, pointeurs avec adresse, déréférencement et écriture, génériques avancés (plusieurs paramètres T, U, tableaux génériques et contraintes exactes), lambdas et fermetures avec retours de type fonction, opérations natives SP3 (maths, texte et tableaux), formules KaTeX dans les notes et références intermodules avec flèches courbes. La simulation s'exécute hors du fil React : Run live par défaut, avec entrées appliquées entre deux frames et Pause/Stop, ou Run borné pour précalculer une trace finie. Le debug et la transpilation JavaScript/Python restent bornés, avec progression et annulation ; le debug ajoute points d'arrêt, mémoire abstraite et valeurs au survol. Run propose aussi une simulation graphique simplifiée. L'interface offre aussi les graphes de contrôle et de dépendances, les cartes Screen/Gauge/ProgressBar/BarChart/LED avec lecture synchronisée à 24 fps, XY plot (Mafs), oscilloscope multicanal (uPlot), les grilles Heatmap fixes suivies par pas sans horloge de lecture, les contrats vérifiables, le gestionnaire de fenêtres, le constructeur de signatures de fonction, les thèmes prédéfinis et personnalisés, huit langues, l'import/export .sp3/JSON, l'autosauvegarde, la récupération des documents neufs, trois sauvegardes de secours et un workspace version 3 : dossier choisi, workspace.sp3, images liées et export ZIP, avec migration des versions 1 et 2. Le mode exercice ajoute un manifeste dans le document : consignes, snapshot de départ, tests d'entrée ou de fonction exécutés par Check, retour du robot, verrou d'édition par mot de passe haché (PBKDF2) et enregistrement d'une solution ZIP lorsque tous les tests passent. Les thèmes ont une apparence sombre et claire commune. Une Discord Rich Presence optionnelle, via un sidecar local sans compte ni token, affiche l'activité courante, un chronomètre et deux boutons GitHub ; seuls des compteurs génériques sont publiés.

Ce qui ne l'est pas encore

Aucun lancement de simulation sans action explicite ; seule la lecture d'une séquence d'écran sans cycle peut relancer la simulation pour renouveler ses images. Les cibles C/C++/Java sont présentes mais désactivées. Les classes fonctionnent sans héritage ni polymorphisme. Les lambdas ont un corps expression unique et ne sont pas génériques ; leurs paramètres ne sont pas adressés par &. Les sauvegardes de secours ne tournent que lors d'un enregistrement direct. Les mutations structurelles du document gardent une analyse synchrone, même si les calculs lourds explicites passent par un Web Worker. Le rendu de monnaie des exemples est glouton pour un jeu canonique, et l'exemple de calcul utilise une intégrale numérique de Simpson. Le mode exercice ne verrouille que l'interface : les tests restent lisibles et modifiables dans le JSON, et le mot de passe ne chiffre pas le fichier.

Comment le projet est conduit

Le développement avance par incréments volontairement petits : une capacité visuelle, puis son modèle de données, puis son moteur, puis ses validations. Une direction de conception n'est jamais implémentée sans être demandée, et une fonctionnalité n'est annoncée que si elle est réellement opérationnelle dans la fenêtre de l'application.

Le code est écrit avec des assistants. Sapphire 3 est un projet conduit en dialogue avec des outils d'assistance au développement (OpenCode, DeepSeek V3.2, ChatGPT Sol 6.1, GLM 3.2, Nemotron de NVIDIA) : c'est un mode de fabrication assumé, pas un détail caché. Ce qui l'encadre : chaque incrément est relu, testé (suite Node et Python, runner Node natif, sans dépendance de test) et validé dans l'interface avant d'être retenu ; la CI GitHub Actions rejoue tests et build sur chaque pull request. Le vocabulaire, les contrats et les limites sont décidés par le projet, pas par le générateur.

Cette documentation évolue avec le projet. Elle décrit l'état atteint, pas un plan. Les pages sont produites en même temps que les fonctionnalités : une capacité ajoutée ailleurs se traduit ici par une nouvelle section ou sous-section, parfois sans nouvelle capture, et une capacité non encore livrée y est explicitement marquée comme absente.
