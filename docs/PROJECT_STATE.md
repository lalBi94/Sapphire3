- Pointeurs : un **type pointeur** `int*` (vers un primitif non void) s'annote sur une variable, une constante ou un paramètre ; l'opérateur **`&`** prend l'adresse d'une valeur stockable (variable, constante, paramètre ou élément de tableau) et l'opérateur unaire **`*`** relit la valeur pointée. Les formulaires proposent les types `T*`, l'opérateur `&` pour un pointeur attendu et `*` lorsque la valeur pointée est attendue. La **simulation locale** et le **debug** les exécutent : `&` produit une adresse (`&nom` ou `&[i]`) et `*p` relit la valeur **courante** de l'emplacement après mutation ; les variables et la mémoire de debug affichent l'adresse. **L'écriture à travers un pointeur est désormais exécutée** : `*p = v` (le slot `target` d'une affectation accepte une `UnaryExpression` `*`) modifie la **valeur réelle** de la variable ou de la case visée, y compris quand l'adresse a été passée à une fonction qui écrit `*param`. La constance est protégée (`*(&const)` refusée statiquement par `PLACEMENT_ILLEGAL` ; marqueur interne d'adresse constante → `SIMULATION_CONST_IMMUTABLE` au runtime, y compris par un pointeur recopié). La **transpilation JavaScript et Python** les prend désormais en charge : une variable adressée vit dans une **cellule** (liste à un élément en Python, jeton d'adresse en JavaScript), `&` renvoie un objet d'adresse et `*p` lit ou écrit la cellule ou la case visée ; l'égalité d'adresses et la protection des constantes sont conservées. La cible **C** utilise des pointeurs natifs pour les variables et paramètres ; l'adresse d'une constante est refusée. C++ et Java restent indisponibles.
- Type fonction et références de fonction : une **signature** `{kind:'function', parameters, returnType}` s'annote sur une variable, une constante ou un paramètre, ainsi que sur le retour d'une fonction ou d'une lambda (primitifs non void, tableaux, pointeurs ou autres signatures en paramètres ; retour primitif ou signature concrète, jamais tableau/pointeur). Une **référence** (nœud `Reference`) vers une `FunctionDeclaration` porte cette signature ; il n'y a pas de nœud distinct « référence de fonction ». La valeur se stocke, se transmet et s'appelle : dans un `CallExpression`, le callee est évalué comme une valeur (fonction directe, lambda immédiate ou variable de type fonction). Les **lambdas** sont décrites ci-dessous. La simulation représente une fonction par `fn nom` et une lambda par `fn <lambda>` ; JavaScript et Python les transpilent nativement, sans helper.
- **Généricité avancée** : une `FunctionDeclaration` peut déclarer jusqu'à huit paramètres de type via `properties.typeParameters` (`T`, `U`…), avec une **contrainte exacte optionnelle**. La propriété historique `generic: true` reste lue comme un unique `T`. Les paramètres sont utilisables sur le retour et les paramètres de leur fonction, y compris comme **éléments de tableau générique** (`T[]`, `U[]`) ; `T*`, `T[][]`, les génériques imbriqués, les variables/constantes/alias génériques et les opérations sur un type non instancié restent refusés. L'inférence se fait sur un **appel direct** : chaque argument est confronté à son motif (`T`, `T[]`…), tous les paramètres déclarés doivent être inférés avec un type identique à chaque occurrence, et la contrainte exacte est vérifiée. Le retour est substitué récursivement et `semantic.genericCalls` publie `types:[{name,type}]`. Aucune spécialisation ni copie d'AST : la simulation exécute la même fonction et les transpileurs émettent une fonction ordinaire. L'interface propose une liste de paramètres de type avec contrainte, `T`/`U`/`T[]`/`U[]` dans les sélecteurs, `<T, U>` sur la fonction et chaque inférence sur l'appel. Le workspace est en version 2 ; les fichiers version 1 sont migrés à la lecture.
- **Lambdas et fermetures** : le nœud d'expression `LambdaExpression` porte un retour (`properties.type`), des `parameters` et un `body` expression unique. Sa valeur a un type fonction concret, peut être stockée dans une variable au type identique, passée en argument, utilisée comme callback `ForEach` ou appelée immédiatement dans le slot `callee`. La capture est **lexicale et par référence** : une lambda peut lire les variables et paramètres visibles, et une fonction peut retourner une lambda qui garde son environnement après le retour (un retour de fonction accepte désormais un **type fonction**). La simulation exécute le corps dans un environnement dont le parent est l'environnement capturé ; JavaScript émet une fonction fléchée, Python une `lambda`. Le corps étant une expression, une lambda ne contient ni affectation ni boucle ; elle ne peut pas être générique et l'adresse d'un de ses paramètres n'est pas prise (`PLACEMENT_ILLEGAL`). L'interface propose l'entrée **Lambda expression**, préremplit ses paramètres depuis le type fonction attendu et ajoute un constructeur de **signature de fonction** au sélecteur de type.
- **Sécurité des données** : un document neuf non vierge sans dossier reste protégé par `sapphire3-recovery/` et restauré au lancement. Un enregistrement direct d'un document existant fait tourner jusqu'à **trois sauvegardes** dans `backups/` (`workspace.backup-1.sp3`…`3`) avant l'écriture atomique ; un échec de copie est signalé sans annuler l'enregistrement. Le nettoyage du dossier de récupération est récursif (fichiers `.tmp` et sous-dossiers) et supprime d'abord le document de récupération ; un nettoyage impossible produit un avertissement distinct, jamais un faux « échec de sauvegarde ». Le format workspace passe en **version 3** avec migration à la lecture des fichiers versions 1 et 2 (`generic` → `typeParameters`, retrait de `screenScale`) ; les versions futures ou malformées sont refusées sans toucher au document courant. Les cartes Image acceptent une référence `images/…` ou une Data URL, jamais les deux.
- **Zoom sémantique** : au-dessus de **21 %** de zoom, les arbres d'instructions complets restent affichés ; de **10 à 21 %**, chaque module montre une **liste compacte de ses fonctions racines** ; à **10 % et moins**, seules les **cartes de modules et leurs liens** restent visibles, annotations comprises. Un badge **Instructions / Functions / Module relations** dans la barre d'état indique le niveau courant, et une recherche de bloc force le retour aux instructions.
- **Moteur hors du fil React** : la simulation, la préparation du debug, la transpilation et les vérifications de cibles s'exécutent dans un **Web Worker** unique (`engine.worker.js`) via `engineRunner.js`. Le worker accuse l'avancement (phases d'analyse, pas de simulation, génération) et l'interface affiche un panneau compact avec pourcentage et bouton **Cancel**. L'annulation **termine immédiatement le worker** et rejette toute demande en cours, puis un worker neuf est créé à la demande. Sans `Worker`, le service garde un repli synchrone. Les mutations structurelles du document conservent leur analyse synchrone, car leurs contrats renvoient immédiatement `ok`/diagnostics au reducer.
- Instruction native `ForEachStatement` (catégorie **SP3 native operations**) : deux slots - `array` (tableau) et `callback` (type `(E) -> void` où `E` est le type d'élément). Le formulaire propose les tableaux et les fonctions de rappel compatibles existants ; une **lambda** peut aussi être insérée directement dans le slot callback. La simulation **copie** le tableau au démarrage puis appelle le rappel par élément (un pas par élément au budget) ; la transpilation JavaScript et Python reproduit ce **passage par recopie** via `sapphireForEach(array, callback)`.
- Opérations natives SP3 : l'instruction **Print** est proposée dans la catégorie dédiée **SP3 native operations** du menu d'insertion (`group: 'native'`, libellé `group.native`) ; elle reste une instruction plaçable dans un corps de module, une fonction ou un bloc. Quatre sous-catégories (`group: 'native.math'`, `native.text`, `native.arrays`, `native.screen`) listent les opérations du registre pur `mathNatives.js`, chacune proposée séparément : **Maths** — `abs`, `min`, `max` (`int` → `int`), `clamp` (`int, int, int` → `int`), `sign` (`int` → `int`), `gcd` (`int, int` → `int`), `pow`, `lerp` (`double, double[, double]` → `double`), `log`, `sqrt`, `sin`, `cos`, `tan`, `floor`, `ceil`, `round` (`double` → `double`), `randomDouble` (aucun paramètre → `double` dans `[0, 1)`) et `randomInt` (`int, int` → `int` inclusif, plage inversée refusée avec `SIMULATION_RANDOM_RANGE`) ; **Texte** — `length` (`string` → `int`), `charAt` (`string, int` → `char`), `substring` (`string, int, int` → `string`), `contains` (`string, string` → `boolean`) ; **Tableaux** — `arrayLength` (tout `T[]` → `int`), `arrayFill` (`int` taille, `int` valeur → `int[]`, sans pas par case), `arrayConvolve` (`int[]`, largeur, hauteur, noyau `int[]`, largeur et hauteur du noyau → `int[]`, cases hors grille à zéro) et `arrayLookup` (`int[]` de compteurs, `int[]` de grille binaire, table de 18 entrées → `int[]`, index `état × 9 + voisins`) ; **Écran** — `screenSetPixel`, `screenGetPixel`, `screenResize`, `screenBlit` (tampon RGBA, dimensions, grille d'indices, palette RGBA) et `screenPresent` (frontière d'image). Le module caché d'un écran exporte aussi `SCREEN_SP3_BLIT_<N>` et `SCREEN_SP3_PRESENT_<N>`. Le nœud `MathCall` (nom historique, libellé **Native operation**) est typé statiquement sans conversion implicite et exécuté par la simulation locale ; un résultat non fini produit `SIMULATION_MATH_DOMAIN`, un indice ou une portion de texte hors bornes produit `SIMULATION_STRING_BOUNDS`. `length`, `charAt` et `substring` comptent des scalaires Unicode et `substring` est exclusif à la fin. Les deux opérations aléatoires sont les seules non déterministes d'une exécution à l'autre. Aucun appel système simulé n'est exposé. Les opérations sont **transpilées vers JavaScript et Python** avec l'équivalent natif le plus direct (`Math.*`, `math.*`, `abs`/`min`/`max`, `len`, `includes`/`in`, `Math.random`/`random.random`, `sapphireRandomInt`/`random.randint`) et de petits helpers pour les entiers BigInt, les arrondis, l'interpolation et les bornes Unicode ; les erreurs de domaine et de bornes conservent leurs codes stables. Exception : `arrayFill`, `arrayConvolve` et `arrayLookup` ne sont pas encore transpilées ; les projets avec écran sont de toute façon refusés par la transpilation.
- Opérations natives tableaux/texte étendues : **huit opérations** ajoutées au registre — `arraySlice`, `arrayConcat`, `arrayContains`, `arrayIndexOf`, `arrayReverse`, `stringSplit`, `stringJoin`, `stringIndexOf`. Les retours tableau sont typés avec le type d'élément réel ; `arrayConcat` exige deux tableaux du même élément, `arrayContains`/`arrayIndexOf` exigent un élément du type du tableau, `stringJoin` exige `string[]`. La simulation copie les tranches, concaténations et inversions sans muter l'entrée, conserve les segments vides de `stringSplit` et compte `stringIndexOf` en scalaires Unicode ; une tranche hors bornes produit `SIMULATION_ARRAY_BOUNDS`. Les deux transpileurs utilisent `sapphireArraySlice`, `sapphireArrayIndexOf`, `sapphireStringIndexOf`, `join`/`split` et la concaténation de copies.
- Écrans pixel SP3 : une carte **Screen** est une grille de pixels 15×9 par défaut, nommable, déplaçable et redimensionnable. **Aucun zoom manuel** : la taille du canvas découle uniquement des dimensions de la carte, mesurées par `ResizeObserver` ; l'application choisit le plus grand **facteur entier** commun aux deux axes, ce qui remplit le cadre au mieux sans jamais flouter les pixels. `screenScale` n'est plus produit ni écrit ; un fichier ancien qui en contient une valeur valide reste lisible, puis l'échelle disparaît au prochain enregistrement. Elle partage son identifiant avec un **module caché normal** qui contient les globales uniques `SCREEN_SP3_GLOBAL_PIXELS_<N>`, `..._WIDTH_<N>` et `..._HEIGHT_<N>` et exporte `SCREEN_SP3_SET_PIXEL_<N>`, `GET_PIXEL_<N>`, `GET_WIDTH_<N>`, `GET_HEIGHT_<N>`, `SET_WIDTH_<N>`, `SET_HEIGHT_<N>`, `BLIT_<N>` et `PRESENT_<N>`. Les opérations natives `screenSetPixel`, `screenGetPixel`, `screenResize`, `screenBlit` et `screenPresent` manipulent un tampon RGBA `int[]` borné à 128×128 ; la simulation et le debug exposent les pixels courants, et la carte les dessine dans un canvas. Pendant **Run**, le moteur conserve une suite bornée d'images : **une par `screenPresent`** si le programme présente ses images, sinon une par écriture native (`screenFrames`, jamais ouverte par une image vide). Chaque carte les rejoue à **24 fps (≈ 41,7 ms)** directement dans son canvas via `putImageData`, sans état React par image, et **toujours vers l'avant** : la lecture ne revient jamais en arrière. Elle boucle sur la période détectée par `findFrameCycle` ; une séquence **fermée** (dernière image identique à la première) compte comme une période, ce qui donne une boucle sans aucun raccord. Une séquence **sans cycle** continue de tourner sur ses images pendant qu'une nouvelle simulation est relancée en arrière-plan ; seules les nouvelles images d'écran, jauges et LED synchronisées remplacent les précédentes dès qu'elles sont prêtes, sans figer l'écran. La trace de nœuds et la sortie du premier Run continuent. Une pause ou un arrêt fige l'image courante. La présence d'un seul écran rend toute transpilation impossible (`TRANSPILE_SCREEN_UNSUPPORTED`). Le tampon de pixels est initialisé en **1×1** puis redimensionné par `screenResize` au démarrage du module caché, afin de ne pas consommer un pas de simulation par pixel sur les grands écrans. L'exemple **Bouncing logos** anime deux logos 2×2 qui **rebondissent** sur les bords de deux écrans **34×18**, façon DVD : vitesses 4 et 2, positions alignées sur les pas pour que la séquence soit **périodique (18 images)** et boucle sans raccord. L'exemple **Matrix rain** fait tomber **trois colonnes** sur un écran **90×18** ; chaque image redessine la tête et sa traînée sans état conservé, donc la séquence est **périodique (18 images)** elle aussi. L'exemple **Game of life** utilise un écran **90×56** (hauteur arrondie de 90/φ) et applique les **vraies règles de Conway** via `arrayFill`, `arrayConvolve`, `arrayLookup`, `screenBlit` et `screenPresent` : des motifs classiques dont les périodes divisent 30 (pulsars, pentadécathlons, clignotants, crapauds, still lifes) évoluent sur 60 générations ; la période 30 étant détectée, la lecture tourne **en boucle avant infinie** et sans raccord.

- Jauge SP3 : une carte **Gauge** affiche un anneau gradué avec dégradé du thème (primaire → condition → sélection) et halo lumineux. Elle partage son identifiant avec un **module caché normal** qui contient les globales uniques `GAUGE_SP3_GLOBAL_VALUE_<N>`, `..._MIN_<N>` et `..._MAX_<N>` et exporte `GAUGE_SP3_SET_VALUE_<N>`, `ADD_VALUE_<N>`, `GET_VALUE_<N>`, `GET_MIN_<N>`, `GET_MAX_<N>`, `SET_RANGE_<N>` et `RESET_<N>` : une jauge se pilote donc depuis n'importe quel module par import. La simulation expose un état par pas (`gaugeFrames`, borné à 8 000) et l'état final (`gauges`) ; la carte suit exactement le focus de nœud pendant Run et le curseur en Debug. Lorsqu'un écran est aussi présent, `screenFrameGauges` capture un état par image d'écran et la jauge l'anime au même rythme fixe de **24 fps**, y compris pendant la lecture en boucle. Une valeur hors plage est affichée telle quelle mais l'anneau est borné. Entre deux valeurs, l'anneau rejoint sa nouvelle position par un **adoucissement bref** (environ 200 ms, facteur corrigé du temps écoulé pour rester régulier si le rendu ralentit) ; le nombre et le pourcentage affichés gardent leur valeur exacte, et la préférence système de **réduction du mouvement** rétablit un saut immédiat. La **grille courbée du canvas** conserve sa géométrie et son comportement ; seules ses couleurs changent. Les animations décoratives permanentes (lévitation de la mascotte, dégradés de survol, comète de focus) ont été retirées ; les indicateurs fonctionnels (progression moteur, flux de debug) restent.
- Direction artistique : géométrie **Void / Acid** et **palette Sapphire par défaut** ; sélections jaunes sur les modules et les nœuds, coins biseautés, surfaces opaques et focus net. La palette **Void / Acid** reste disponible ; les tokens communs couvrent palette, courbures, espacements, ombres et transitions de 120 ms. Repli opaque sans `backdrop-filter`, préférences de réduction du mouvement et de la transparence respectées.
- Robot de notification : chaque palette définit `--mascot-filter` dans `tokens.css` et `ThemeContext.jsx` ; Sapphire garde l'identité (`brightness(1)`), les autres palettes appliquent une teinte `sepia` + rotation de teinte assortie à leur couleur principale.
- Typographie embarquée dans `src/styles/fonts.css` et `src/assets/fonts/` : **Inter** pour le texte courant, **Space Grotesk** pour les titres, noms de modules et intitulés de sections (`--font-display`), **JetBrains Mono** pour les données techniques (`--font-mono`). Les fichiers woff2 sont servis localement, sans requête distante à l'exécution ; les sous-ensembles latins et cyrilliques sont fournis, les autres écritures retombent sur les polices système. Les ligatures contextuelles sont désactivées pour laisser les opérateurs du code exacts. Licences OFL conservées dans `public/fonts/licenses/`.
- Les actions de menus, de statut, de propriétés et de formulaires utilisent des icônes Lucide React ciblées, avec tailles, épaisseur et attributs d'accessibilité cohérents.
- Micro-interactions CSS sans JavaScript dans `src/styles/interactions.css` : anneau « comète » à deux têtes opposées (jaune et violette, traîne décroissante sur base sombre visible en permanence) tournant en 2,6 s autour des champs ciblés au focus (formulaire de nœud, renommage de module, légende d'image), avec halo extérieur pulsé de 1,9 s. Les **boutons d'action** — bouton `+`, Save/Create, Run, confirmation, export/copie du panneau Transpiler, actions du menu logique — n'utilisent plus cet anneau ni aucun pseudo-élément animé au survol : leur retour stable vient des fonds, bordures et couleurs des composants, ce qui supprime les tremblements de rendu. Le menu de nœuds, les actions du menu logique et Run conservent seulement un dégradé de fond animé, sans déplacement ni ombre projetée. L'anneau de focus épouse exactement la bordure du composant (`inset: -1px`, `border-radius: inherit`, `corner-shape` explicite). `outline :focus-visible` reste conservé, l'effet est désactivé en contraste renforcé et couleurs forcées, et les animations sont coupées en mouvement réduit. Les classes `.glow` et `.glow--halo` restent disponibles pour les champs ; bordures de catégorie des nœuds, sélection, glisser-déposer, erreurs et debug ne sont pas touchés.

## Contrats et décisions

- Source logique v1 : projet avec modules et tableau global de Nodes ; relations distinctes pour propriété `moduleId`, imbrication `children` et cibles symboliques `references`. Contrats détaillés dans `docs/LOGIC_API.md`.
- AST et données sémantiques dérivés, indépendants des langages, de React, du rendu et des API natives. Identifiants injectés par l'appelant et conservés. Source non mutée ; erreurs bloquantes n'empêchant pas sa représentation ni l'inspection de l'AST.
- Portées module/fonction/bloc/for ; déclarations précollectées, sans analyse générale de l'ordre d'initialisation. Typage explicite obligatoire (y compris littéraux), dix primitifs autorisés seulement, aucune conversion implicite ou valeur de type de secours. S'y ajoutent le type tableau `{kind:'array', elementType}`, le type pointeur `{kind:'pointer', pointee}` (cible : primitif non void), le type fonction `{kind:'function', parameters, returnType}`, le type de classe `{kind:'class', classId}` et le paramètre générique `{kind:'generic', name:'T'}` limité à la signature de sa fonction, annotables sur les variables, constantes, paramètres et retours ; `&` prend l'adresse d'une valeur stockable et `*` (unaire) relit la valeur pointée. Alias transparents vers ces primitifs, signatures de fonctions complètes. Les tableaux et pointeurs de classes restent refusés. Une expression non typable est absente de `semantic.nodeTypes` et présente dans `untypedNodeIds` ; symbole sans type résolu : propriété `type` absente.
- `CastExpression` encode les conversions numériques explicites et identités non void ; entiers signés/non signés 16/32 bits exacts, flottants IEEE 754 32/64 bits. Contrôles statiques des dépassements, sous-flux vers zéro et divisions par zéro prouvables ; pas de wrap ni d'analyse globale d'intervalles. La simulation réutilise ces contrôles pour les valeurs non constantes ; les futurs backends devront aussi respecter ce contrat.
- Fonction non void : retour exigé via contrôle conservateur des blocs et des deux branches d'un if, sans preuve via les boucles. `char` : scalaire Unicode unique. Format JSON v1 conservé, anciennes annotations désormais invalides mais jamais migrées silencieusement. Préférer les littéraux numériques textuels pour préserver leur écriture exacte, dont `'-0'`.
- Les conteneurs visuels ont un identifiant UUID, un type stable `module`, `class`, `comment` ou `image`, une position `x/y` et des dimensions `width/height` en unités monde. Valeurs initiales : 320 × 220 pour Module/Comment, 340 × 240 pour Class, 420 × 260 pour Image ; minimum commun 180 × 120. Catalogue énumérable centralisé dans `moduleTypes.js`, avec `sourceKind` seulement pour les cartes logiques. Présentation exportée séparément de la source dans l'enveloppe workspace.
- Les cartes suivent la translation et le zoom, avec des rectangles non déformés ; la courbure reste un effet décoratif du quadrillage. Déplacement individuel et noms visuels personnalisables pour Module/Comment. Suppression confirmée des deux types de cartes.
- Les cartes Module et Class partagent l'identifiant de leur module source ; leur nom est synchronisé avec le module logique. Comment réutilise le cadre visuel sans entrer dans `moduleKinds` ni dans la source logique ; son titre et son texte restent purement UI.
- Classes : la carte **Class** crée un module source `kind: 'class'`, nommable et déplaçable comme un module. L'arbre affiche deux scopes **Public** et **Private** ; seuls `VariableDeclaration`, `ConstantDeclaration` et `FunctionDeclaration` (constructeur compris) sont acceptés à la racine. Chaque membre porte `properties.visibility` (`public`/`private`), et le constructeur porte `properties.constructor: true`, le nom `constructor`, un retour `void` et une visibilité. Le badge `Class` et l'accent de sélection distinguent la carte. `NewExpression` instancie la classe, `ThisExpression` désigne l'instance courante, `MemberExpression` lit ou appelle un membre ; `CallExpression` peut appeler une méthode et `AssignmentStatement` peut cibler un attribut. Le type `{kind:'class', classId}` est annotable sur les variables, constantes, paramètres et retours. Les membres privés ne sont accessibles que dans leur classe ; un constructeur privé ne se crée que depuis sa classe. Aucun héritage ni polymorphisme. La simulation crée l'instance, initialise les attributs, exécute le constructeur et lie `this` aux méthodes ; les modules de classe sont ignorés à l'initialisation globale. La transpilation JavaScript/Python émet une classe avec ses champs, son constructeur et ses méthodes : les initialiseurs de champs sont évalués dans la portée appelante, `this` est lié aux méthodes et les méthodes passées en callback restent liées. La visibilité public/private reste une règle d'analyse, non une barrière runtime dans le code généré.
- Les positions et dimensions des cartes restent hors de la source logique. Les nœuds logiques sont rendus dans leur conteneur avec slots, types résolus et compteurs de diagnostics. Le pliage des nœuds reste un état UI local, sans effet sur la source ni l'AST.
- Insertions : jamais de remplacement d'un slot unique occupé, jamais de réutilisation d'un enfant existant dans un bundle neuf, ordre conservé dans les listes, identifiants stables, réanalyse systématique avec comparaison des diagnostics pour rejeter atomiquement une insertion qui introduirait une erreur dure. Les états incomplets (littéral sans valeur, appel partiel, retour sans argument) restent éditables sans bloquer l'édition.
- Contraintes de résultat connues (littéral typé, cast, opérateur déterminé) contrôlées même avant complétion des enfants ; opérateurs filtrés selon le type attendu du slot.
- Suppression : `deleteSourceNodes` retire le nœud visé et ses descendants, puis délie son entrée du parent. Les autres identifiants et références restent inchangés ; les liens supprimés deviennent `REFERENCE_UNRESOLVED`. Les cartes Module ont leur suppression distincte. L'API pure n'a pas d'historique ; l'UI assure undo/redo. La suppression d'Image/Comment ne touche qu'à la présentation.
- Caméra en mémoire React, restaurable par import/export manuel : `x` et `y` désignent le point du monde au milieu de la vue, axe Y positif vers le bas ; `zoomLevel` est un exposant en base 2 (0 = 100 %, 2 = 400 %). Le déplacement en pixels est converti selon le zoom.
- Seules les lignes visibles sont tracées via un décalage périodique ; leur espacement monde double progressivement au dézoom pour maintenir une densité raisonnable. Pas de surface géante ni d'accumulation. Les bornes dynamiques attendent une future demande.
- Aucune bibliothèque de nœuds, UI ou gestion d'état ajoutée.
- Client Neutralinojs 6.10.0 embarqué pour les dialogues et fichiers uniquement ; API natives regroupées dans le service, sans réseau distant. Fermeture du processus toujours gérée par la fenêtre native.
- Emplacements internes Neutralinojs configurés sur `system`, sans stockage métier. État de fenêtre non sauvegardé.
- `bin/`, `dist/`, `build/` et fichiers temporaires ignorés par Git.

Sans certificat, la construction signale explicitement un paquet non signé ; aucun certificat n'est stocké dans le dépôt.

Corrections récentes : lien d’évitement vers le canvas, tableaux accessibles des graphiques, `role="img"` sur l’écran, retour de focus des confirmations, cibles de 24×24, suppression des régions dupliquées de l’arbre logique, zone défilante des paramètres focalisable, région live de simulation limitée aux changements d’état. Limites connues : bordures sous 3:1, pas d’alternative au clic seul pour déplacer/redimensionner les modules et panneaux, erreurs de formulaire non reliées au champ, pixels d’écran sans équivalent textuel, tests NVDA/Narrator et WebView2 non exécutés.

La **CI GitHub Actions** (`.github/workflows/ci.yml`) s'exécute sur chaque **pull request** : installation verrouillée, contrôle des espaces, marqueurs de conflit et tests focalisés, `pnpm test` (Node et Python) puis `pnpm build`. Aucun secret ni droit d'écriture n'est demandé.
- `pnpm preview` n'a pas été exécuté séparément.
- Le « dézoom infini » reste soumis aux nombres JavaScript : les changements créant une échelle nulle ou une position non finie sont ignorés. Aucun seuil minimal de confort n'est imposé. Pas de zoom tactile par pincement.
- L'autosauvegarde réécrit le fichier `.sp3` associé ou, pour un document jamais enregistré non vierge, une copie de récupération dans le répertoire de données persistant ; un document vierge n'écrit rien. Après une première sauvegarde, chaque modification est réécrite dans le fichier et celui-ci est rouvert au lancement. La transpilation reste manuelle et ne modifie jamais la source.
- Lambdas : le corps est une expression unique, donc aucune affectation, boucle ou `return` à l'intérieur ; les captures sont en lecture et une lambda ne peut pas être générique. `&` sur un paramètre de lambda est refusé ; les pointeurs reçus restent utilisables. Les fermetures créées dans une boucle suivent les règles de capture de chaque backend, sans normalisation supplémentaire.
- Pas de position libre individuelle des nœuds ni de choix d'index d'insertion : les transferts visent le nœud/module receveur et ajoutent à la fin de l'unique slot compatible. Un corps de fonction déjà présent est un enfant unique : viser son bloc pour y ajouter des instructions. Pas d'édition directe des enfants dans les propriétés (navigation seulement). La copie de modules entiers couvre les modules logiques et les classes ; les modules de widgets demandent une réindexation dédiée et restent refusés. Un module copié conserve ses imports externes, qui doivent déjà exister dans le workspace cible. Undo/redo n'est pas un historique complet des gestes et des saisies d'annotations. Aucune migration implicite des données UI.
- Debug : trace préparée avant navigation, sans édition des valeurs mémoire ni entrée interactive. Les points d'arrêt visuels sont locaux à la session. Budget de pas et d'appels de la simulation, plus 200 000 entrées d'instantanés retenues et un état terminal. Analyse d'accessibilité conservatrice : pas de preuve générale de terminaison, de valeurs de variables ou de comparaisons arithmétiques. La **simulation graphique simplifiée** est une option explicite de Run, distincte du debug ; elle ne trace que les appels directs entre fonctions atteignables.
- CFG d'inspection : intraprocédural, expressions et appels atomiques ; branches conservées sans propagation des valeurs constantes. Le graphe de dépendances montre les relations directes et l'imbrication, pas une fermeture transitive des fonctions appelées. Ces graphes restent distincts de la simulation graphique simplifiée. Aucun layout automatique sophistiqué ni bibliothèque de graphes ajouté.
- Les fonctionnalités existantes des incréments Copilot (images, simulation, thèmes, français, historique et préférences) sont désormais confirmées par l'utilisateur et intégrées à `AGENTS.md`. Les cibles de génération actives sont JavaScript, Python et C expérimental ; C++ et Java restent indisponibles. Aucune extension générale de la simulation, moteur de suggestions ou publication implicite n'est autorisée par cet incrément.
- Moteur : source JSON v1, ancienne catégorie `main` conservée et diagnostiquée `MODULE_INVALID`, version inconnue conservée et signalée. Import UI : structure affichable et versions connues exigées ; un workspace est un dossier contenant `workspace.sp3` (20 Mio maximum), `images/` et `backups/` ; l'import d'anciens `.sp3`/`.json` reste limité à 20 Mio ; anciennes catégories Main et versions inconnues refusées sans remplacer le document. Aucune migration automatique. Profondeurs de sécurité autour de 200 niveaux.
